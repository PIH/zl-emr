# Form availability — Haiti / Zanmi Lasante (ZL)

When is each of the ZL forms (27, plus `checkin_v3.5`, `vitals_v2.2` and the four `patientRegistration-*`) offered to a user? Written once for all forms; specs cite the form's row.

**Sources (local checkouts, 2026-10-26):** `openmrs-module-pihcore` `322f9252` (2026-10-23, branch `duplicate-patient`; uncommitted changes only in the registration app files, not read) `api/.../apploader/{CustomAppLoaderFactory,RequireUtil,CustomAppLoaderUtil,CustomAppLoaderConstants}.java`, `PihEmrConfigConstants.java` (line numbers below are `CustomAppLoaderFactory.java` unless stated); `pihemr` `0b48ae68` (branch `UHM-9524`) `scripts/visit/encounterTypeConfig.js` (byte-identical to `zl-emr/distro/target/.../pih/scripts/visit/encounterTypeConfig.js`; `zl-emr` has no copy of its own); `zl-emr` `fccdaa5` `pih-config-haiti*.json`. pihcore is a SNAPSHOT dependency, so the local test server (:7071) may run a different build; not checked.
**Not covered:** the other `_v*` copies (`checkin_v3.5` and `vitals_v2.2` are specced), `hiv/iSantePlus/*`, O3/SPA, the other Haiti forms (primary-care-*, ncd-*, ...), and every other country branch.

## Shared layers (apply to every row below)

1. **Entry point = visit action** (`visitAction`, extension point `...visitActions`) on the visit page, unless the row says otherwise. Link: `htmlformentryui/htmlform/enterHtmlFormWithStandardUi.page?patientId=<uuid>&visitId=<id>&definitionUiResource=file:configuration/pih/htmlforms/<form>.xml` (check-in uses `enterHtmlFormWithSimpleUi.page`). HIV, PMTCT and EID links append `&returnUrl=/openmrs/pihcore/visit/visit.page?patient=<uuid>&visit=<uuid>#/overview` (`patientVisitsPageWithSpecificVisitUrl`, :219). Registration actions append `&createVisit=true`. `...WithoutVisit` links carry no `visitId`.
2. **Component flag**: see the tables above. Country branch: only `enableCheckIn` (:639, `isCountry(HAITI) && !isSite("HSN_SAINT_MARC")`) and `enableVitals` (:730 Haiti branch: Standard UI, no inpatient-tag exclusion, no MCH/pregnancy/infant clones) branch on Haiti for our forms.
3. **Privilege** (`requiredPrivilege` on the extension, plus any `userHasPrivilege` in `require`). Checked by name against `user.privileges`, so a role is not enough.
4. **Session location tag**: `sessionLocationHasTag("<tag>")` against the location the user chose at login. The XML's own `<encounterLocation tags=...>` is a separate, second check (see "On ENTER").
5. **`require` expression**, evaluated in the visit-page context (`patient`, `visit`, `sessionLocation`, `user`, `encounters` = all of the patient's encounters). Helpers (`RequireUtil`):

| Helper | Expression |
|---|---|
| `retro` (my shorthand) | `or(and(hasPriv(<enter-note priv>), patientHasActiveVisit()), hasPriv("Task: emr.retroConsultNote"), and(hasPriv("Task: emr.retroConsultNoteThisProviderOnly"), patientVisitWithinPastThirtyDays))`; `<enter-note priv>` is `Task: emr.enterHIVConsultNote` / `enterVitalsNote` / `enterConsultNote` per row |
| `patientHasActiveVisit()` | `visit != null && visit.stopDatetime == null` |
| `patientVisitWithinPastThirtyDays` | with `visitNote`: `(now - new Date(visit.stopDatetime)) / day < 30`. Always false for a still-open visit (`new Date(null)` = 1970) |
| `visitDoesNotHaveEncounterOfType(t)` | `visit && !some(visit.encounters, type == t)`: the *current visit* only |
| `not(patientHasPreviousEncounter(t))` | `!(encounters && some(encounters, encounterTypeUuid == t))`: **any earlier visit** counts |
| `patientIsFemale()` / `patientIsReproductiveAge()` | `patient.person.gender == 'F'` / `patient.person.age >= 10` (current age) |
| `patientAgeInMonthsLessThanAtVisitStart(n)` | `fullMonthsBetweenDates(birthdate, visit.startDatetimeInMilliseconds) < n` |
| `sessionLocationDoesNotHaveTag(t)` | `sessionLocation` defined and lacks tag `t` |

6. **Extra entry points**: `cloneAsHivVisitAction` re-registers a visit action (same privilege and `require`) on the HIV program dashboard (`/pihcore/router/programDashboard.page`); clones exist for HIV intake, followup, psychosocial, dispensing and vitals. `HIV_VISIT_ACTIONS_ORDER` (CustomAppLoaderConstants :619) omits the psychosocial clone.
7. **View / edit / print** of a saved encounter is configured in `encounterTypeConfig.js` (below), not here. Edit always opens the Standard UI (`editHtmlFormWithStandardUi`) except check-in and Haiti vitals v2.2 (Simple UI).

### Test location "Klinik Ekstèn" (Mirebalais)

Session tags (from the brief, not queried): Mental Health, HIV Consult, Primary Care Consult, NCD Consult, Check-In, Consult Note, Vitals, Drug Order; the code spells them "<name> Location". The `Oncology Consult Location` tag is not among them, so `vct`'s exclusion passes. It has none of `Vitals Inpatient Location` / `Vitals ANC Location` (the tags of the two unreferenced vitals forms). So at CEN, Klinik Ekstèn satisfies the tag layer of every offered row; a spec only needs the component, privilege and patient/visit layers.

### On ENTER: the five wrappers (`hiv-intake`, `hiv-followup`, `pmtct-intake`, `pmtct-followup`, `eid-followup`)

55-line header forms (`pmtct-followup` 58): only the `encounter-provider-location-date` subform with `<encounterLocation default="SessionAttribute:emrContext.sessionLocationId" tags="HIV Consult Location"/>`. `ifMode ENTER` hides the form and calls `submitHtmlForm()` when `encounterLocation.value` is non-empty, so at Klinik Ekstèn (has the tag) opening the URL saves an empty encounter and redirects to `returnUrl` (or home). At a session location **without** the tag the select starts empty, the form is shown (`#next` hidden) and the user must pick a location. Provider defaults to the current user (role `4f10ad1a`); if the user is not a valid provider for that role the required provider is blank and the hidden form cannot submit (unverified what the user sees). EDIT shows the form and calls `setUpNextAndSubmitButtons()`. `prep-*`, `vct`, `hiv-psychosocial` and `hiv-dispensing` are **not** wrappers: they are full forms, and `prep-*`/`vct` are viewed through their own `templateModelUrl`.

### Check-in at CEN versus HSN

`enableCheckIn` picks `checkin_v3.5.xml` (formUuid `2bbd0788...`, dropdown fed by global property `haiti.checkIn.reasonsForVisit`) for every Haiti site except `HSN_SAINT_MARC`; only HSN gets `checkin.xml` v4.0 (formUuid `660f4e34...`, fixed checkbox list). So at CEN, `checkin.xml` is reachable by direct URL, or through the registration-summary "most recent check-in" widget's edit link (:1852, non-SL branch), which names it explicitly; this is the live path to `checkin.xml` at CEN. (`registerTemplateForEncounterType` :704 also names it, but its own TODO says it serves the old patient-visits page, not `visit.page`.) The visit-page edit pencil (`encounterTypeConfig.js` :806, `hfeSimpleEditUrl`) names no form, so it reopens the form the encounter was saved with.

## Visit-page sections (`section-*.xml`)

`section-*.xml` are **not** included by the entry forms (no `<subform path="...section-...">` in any ZL form). Each is a standalone form that is the view template (`templateModelUrl`, `getAsHtml.action`) and edit link (pencil, `editHtmlFormWithStandardUi.page?patientId=&visitId=&encounterId=&definitionUiResource=file:configuration/pih/htmlforms/hiv/section-<x>.xml`) of an `encounter-section` in `encounterTypeConfig.js`. They have no encounter type of their own and are meaningful only in EDIT on the parent encounter. Resolution (`EncounterTypeConfig.get`, end of file): `encounterTypes[uuid]` -> `[country]` (`haiti`; then `[site]` else `DEFAULT`) or `DEFAULT`, then `versions[encounter.form.version]` else `versions.DEFAULT`. Both shapes used by the HIV types (`{DEFAULT:{versions}}` and bare `{versions}`) resolve to `versions` for Haiti.

|---|---|
| HIV intake (`hiv-intake`; `c31d306a`). ## Fixture recipes

- **Standard visit-action form at CEN** (`vitals`, `outpatientConsult`, `vct`): patient with an **active** visit at the session location, session at Klinik Ekstèn, user holding the row's privilege (`Task: emr.enterVitalsNote` / `enterConsultNote` / `enterVCT`) or `Task: emr.retroConsultNote`. For `vct`, no VCT encounter yet in the visit.
- **HIV-program forms**: not offered at CEN. Either run against `hiv-ci` (`OPENMRS_PIH_CONFIG=haiti,haiti-hiv,haiti-hiv-ci`) with a session location tagged HIV Consult Location, or open the entry URL directly (skips every gating layer above). Requirements to satisfy when exercising the gate: `hiv-intake` patient without any earlier HIV intake; `pmtct-*` female age >= 10; `eid-followup` birthdate less than 24 full months before the visit start; `prep-*`/`vct` no Oncology tag.
- **`hiv-drug-order-documentation`**: needs an existing drug order. Create it over REST (an encounter plus a `drugorder` for the patient), then open the EDIT URL on that encounter.
- **`checkin.xml`**: HSN profile for the real entry (visit action or registration action), or the direct URL `enterHtmlFormWithSimpleUi.page?patientId=<uuid>&visitId=<id>&definitionUiResource=file:configuration/pih/htmlforms/checkin.xml` at CEN.
- **Sections**: create the parent encounter over REST (type uuid in the table), open the section's edit URL directly (`SectionFormPage`); this skips all gating above.
- **Unreferenced forms** (`liveCheckin`, `vitalsInpatient`, `vitalsPregnant`, `section-risk-factors`, `section-symptoms`): only the direct entry/edit URL exists. `vitalsInpatient`/`vitalsPregnant`: the location select starts empty at Klinik Ekstèn (their tags are absent), so a test picks a location.
- **Admin user**: privilege checks match the privilege name against `user.privileges`; whether a superuser's list contains every privilege name is unverified, so check one visit-page render before relying on it.

## Confirmed by the e2e specs (local ZL test server, `haiti,haiti-central,haiti-local-idgen`, 2026-10-26)
What the specs showed about reaching the forms. The harness logs in as a non-superuser admin account with session location "Klinik Ekstèn" (Mirebalais), which carries the HIV Consult, Check-In, Vitals, Consult Note, Primary Care Consult and NCD Consult tags, and creates visits at "Mirebalais".

- **Direct URLs skip the gating.** `enterHtmlFormWithStandardUi.page` (entry forms, in a visit created over REST) and `editHtmlFormWithStandardUi.page` (section forms, on an encounter created over REST) open without the component, privilege or visit-page requirements in the rows above. None of the HIV forms is offered on `haiti-central` (only `haiti-hiv` offers them); the specs reach them by URL. The gating itself is not tested.
- **HIV wrappers.** `hiv-intake`, `hiv-followup`, `eid-followup`, `pmtct-intake`, `pmtct-followup` auto-submit in ENTER because the encounter location (tag `HIV Consult Location`) has a value at Klinik Ekstèn; the saved encounter is at that location, in the visit, and has a form. EDIT shows the form (heading, location and date selects, `#next`, `#cancel`). `pmtct-followup` shows the "HIV Followup" heading (V2 above). The "location empty, form shown" path needs a session location without the tag and is not covered.
- **Simple vs Standard UI.** `vitals.xml` is entered with the Standard UI. `vitalsInpatient.xml` and `vitalsPregnant.xml` are unreferenced (nothing launches them) and their unit converters are ExitHandlers, which only the Simple UI defines (`enterHtmlFormWithSimpleUi.page`; the Standard UI throws "ExitHandlers is not defined"), so their behaviour tests use the Simple UI. `checkin.xml` is opened through the Simple UI, as production does for the check-in forms.
- **Location select, by form.** `vitalsInpatient`: tag `Vitals Inpatient Location` has no location on this server, so the select is empty and required (the spec copies the session location's option value into it). `vitalsPregnant`: `Vitals ANC Location` has options and the session location is preselected. The HIV wrappers and the forms that include `encounter-provider-location-date.xml` with `HIV Consult Location` preselect Klinik Ekstèn.
- **Reachability of section forms.** `section-risk-factors` and `section-symptoms` are unreferenced (no UI path). `section-hiv-assessment` is offered only under HIV intake and PMTCT intake, but its adverse-event and health-condition blocks render only for the HIV followup type (unreachable from the visit page, Low). `liveCheckin.xml` is unreferenced; at this site check-in is entered with `checkin_v3.5.xml`, which has no spec.
- **Program side effects of a save** (asserted in the specs): HIV program on `section-hiv-history` (child or infant, per age and type), `section-hiv-state`, `section-pmtct-history`, `section-hiv-plan` (adult yes, 1-year-old no) and not on `section-hiv-assessment` for a 1-year-old; EID program on `section-eid-protection` (exactly EID) and on `section-hiv-history` for an infant; PrEP program on `prep-followup` (`prep-intake` has no enrolment).
- **Orders.** Saved in the specs for `section-eid-protection`, `section-hiv-plan` (other-drugs widget), `prep-intake`, `prep-followup` and `hiv-drug-order-documentation` (asserted through REST on the synthetic patient). `hiv-dispensing` writes obs only. Not saved: lab orders (`pihLabOrder` in `section-eid-plan`) and the ART order widget in `section-hiv-plan`.
- **Save effects found while testing.** `outpatientConsult` with ED Observation saves the encounter, diagnosis, disposition and comment obs, leaves the visit open and the patient alive; Admission and Death make their extra field required (those saves are not exercised).
